# Pass 6 transactional email implementation map

This document records the V1 transactional email surface implemented on the isolated Pass 6 candidate. It does not authorize changes to the frozen Backend #160 or Frontend #94 candidates, sending to Guests, or a staging/deployment operation.

## Product decisions

- Event cancellation, postponement, and other qualifying material-change notices go to each current ticket holder. Purchaser contact is the fallback only when no active entitlement identifies a holder.
- Refund financial notices go to the purchaser tied to the order. A verified purchaser account is required when the order has a user ID; the saved order contact address is used only for guest checkout without a user ID.
- Refund email is sent only on the founder-selected canonical outcomes: settled/completed and declined/rejected. Provider-failed refunds remain an operational state and do not generate a transactional email. Intermediate requests and provider processing states do not send a final-outcome message.
- Ticket assignment acceptance has no separate confirmation. The recipient gets the invitation; accepted ticket issuance remains governed by the canonical ticket-issuance event.
- Accepted ticket transfers notify the new holder and the verified former holder.
- KYC/onboarding V1 sends submission receipt, changes requested, approval, and final rejection messages when the corresponding canonical state is supported.

## Trigger and authority map

| Email family | Durable trigger / source of truth | Recipient authority | Delivery behavior |
| --- | --- | --- | --- |
| Purchase receipt / RSVP | `order.fulfilled`; paid order and non-pending fulfillment state | Saved order contact | Stable order idempotency key; no provider call before durable email-delivery record |
| Ticket assignment invitation | Existing persisted pending transfer created for the assigned admission | Persisted verified recipient account or exact persisted recipient-email binding | Invitation token is not placed in the message; scoped transfer URL opens the claim flow |
| Transfer invitation resend | `ticket.transfer.invitation_resent` and persisted pending transfer | Same persisted recipient binding as initial invitation | Request ID distinguishes an intentional resend; transfer ID remains stable |
| Ticket issuance / upgrade | `ticket.issued` plus persisted entitlement and completed order where required | Canonical current holder; issuance-to-holder suppresses purchaser duplicates | Stable entitlement/holder or upgrade key |
| Transfer accepted | `ticket.transfer.resolved` accepted and matching credential version | Current holder and separately verified former holder | Two recipient-specific idempotency keys |
| Transfer expired | Canonical expired transfer resolution | Verified former holder | No ticket movement is inferred from email delivery |
| Waitlist offer / expiry | `waitlist.offered` or `waitlist.expired` matching persisted entry and reservation | Verified waitlist account | No automatic payment claim; offer expiry is checked against current state |
| Partner application | `partner.onboarding.email_requested`; current persisted application status | Applicant account from user directory | Submission, changes requested, approved, final rejected; reviewer note is escaped and limited to the applicant-facing note |
| Promoter assignment / suspension | Canonical promoter assignment or status event and persisted organization ownership | Persisted organization owner | Invitation/status/expiry and suspension messages; no marketing fanout |
| Event cancellation | `event.cancellation.email_requested` generated by cancellation fanout | Current holder, purchaser fallback only if no active entitlements | One deterministic durable event per recipient/order |
| Event postponement / material change | Canonical material-change fanout and current event/entitlement state | Current holder; purchaser fallback for legacy order-level events | Communicates current event details, ticket validity, and applicable refund-request rights |
| Refund settled / rejected | `finance.refund.settled` or rejected `finance.refund.finalized`, validated against current refund record | Purchaser only | Only completed and declined outcomes email; provider-failed status remains operational and is not emailed |
| Refund review requested | Canonical refund review event and persisted entitlement/order | Requesting ticket holder | Request acknowledgment only; not a completion notice |
| Payment support required | Canonical payment state event | Payment/order contact derived by the consumer | Support path only; no payment secret or token in the link |
| Payout status | Canonical payout state event | Existing authorized partner owner/contact | Status only; no payout feature or worker is enabled by this pass |
| Event cover / ticket add-on | Canonical redemption/reversal/refund event and persisted account or entitlement | Account guest/current ticket holder | Amount and event-specific operational notice |

Password reset, OTP, and staff-invitation flows remain on the existing `EmailSender` methods. In development/test without provider credentials they retain their existing suppressed behavior; this pass does not capture one-time codes, reset tokens, or temporary passwords as transactional evidence. Event reminders and Marketing Blast delivery are intentionally out of scope.

## Delivery architecture

Business services append domain events/outbox records alongside canonical state transitions. The transactional-email consumer validates the persisted state and server-derived recipient, creates a deterministic `MAIL-…` delivery record, then claims it under a lease before calling the provider. Firestore stores delivery state without message body or raw recipient; only a SHA-256 recipient hash is stored. Resend receives the stable idempotency key. A provider message ID is recorded only after a successful provider response. Local development/test capture is explicitly `captured`, has no provider message ID or sent timestamp, and stores structured rendered evidence only in process memory.

Retryable provider errors are reduced to a safe durable error class and rethrown so the outbox can retry. Known permanent 4xx errors are marked `permanent_failure` and are not retried. A process interruption leaves the durable intent and lease; the Firestore repository permits recovery once the lease expires. Provider acceptance is not represented as inbox delivery.

The existing Admin communications route is read-only and role-protected. It exposes delivery metadata and provider request ID, strips the recipient hash, and does not return rendered content. There is no retry or content-inspection route; no broad email admin UI is added.

## Sender and links

The server reads `RESEND_API_KEY` and the explicit `RESEND_FROM_EMAIL` setting. The sender address is not hardcoded in runtime provider requests. A provider request fails closed if credentials exist but no sender identity is configured. Development/test sends are captured by default even if a key exists; an exact `RESEND_NON_PROD_TEST_RECIPIENT` match is required to make an intentional non-production provider request. The checked-in `.env.example` documents these settings without supplying a real address or secret.

Guest ticket, transfer, help, and terms links use the validated `GUEST_PORTAL_URL` origin. Partner application/workspace links use the configured Partner Dashboard URL, with a sign-in fallback when it is absent. Current frontend routes include `/tickets`, `/ticket-transfer/[transferId]`, `/help`, `/terms`, `/onboard`, and the partner workspace paths used by their templates.

## Template system and evidence

All standard transactional bodies use the shared email-safe C1RCLE shell: hidden non-repeating preheader, table-based 100%/620px layout, inline styles, dark foundation, orange accent, readable heading/body hierarchy, and wrap-safe text. A plain-text alternative is generated with CTA labels and URLs. No QR or private ticket token is embedded in email. Local captures include delivery-intent ID, sender identity when configured, recipient, template type, subject, preheader, HTML/text, idempotency key, and capture timestamp.

## Privacy and overlap

- Guest self-service endpoints added by Pass 6: none. Provider invocation remains in the server-side outbox consumer.
- Admin delivery evidence: authorization is checked by `AdminOperationsService`; public HTTP serialization omits `recipientHash` and no content field exists on the delivery record.
- Recipient selection is derived from canonical order, entitlement, transfer, user, application, or organization records. No caller-provided recipient is accepted by the transactional consumer.
- Frozen #160/#94 worktrees are not modified. Pass 6 overlaps M3 ticket holder/transfer and event-lifecycle events, M4 refund/payment outcomes, and Auth/KYC identity/application events only at their existing contracts; no ownership, refund, payment, Auth, or KYC decision semantics are rewritten.

## Acceptance boundary

Focused local evidence is indexed in [ACCEPTANCE_EVIDENCE.md](./ACCEPTANCE_EVIDENCE.md). All 38 currently implemented V1 review renders and text alternatives are indexed in [EMAIL_DESIGN_VISUAL_ACCEPTANCE.md](./EMAIL_DESIGN_VISUAL_ACCEPTANCE.md). Desktop/mobile screenshot capture and founder visual approval remain outstanding because the browser environment refused `file://` and prohibited alternate rendering routes. Real Resend acceptance requires a legitimate configured non-production API key and verified sender/domain, limited to a founder-controlled test recipient. If those are unavailable, the result is **HOSTED/PROVIDER ACCEPTANCE REQUIRED**. No email is sent to a real Guest, and no inbox-delivery claim is made from a provider acceptance response.
