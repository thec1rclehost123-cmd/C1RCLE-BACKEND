# M5 Migration and Rollback Plan

This is a planning artifact only. No live backfill, migration, index deployment, or destructive data operation is authorized.

## Rollout order

1. Add optional/versioned contract fields and domain decoders that preserve legacy records without manufacturing holder, eligibility, access grant, cover balance, or policy approval.
2. Add persistence/repository operations and composite indexes. Validate all query shapes and transaction behavior in Firestore Emulator.
3. Deploy backend readers/writers and server-enforced flags disabled. Old clients continue to read legacy DTO shapes through explicit compatibility mapping.
4. Deploy Guest, Partner, Admin and scanner clients that handle unavailable/disabled states. Keep new write actions hidden or rejected while flags/approval are false.
5. Run a read-only inventory and dry-run report against approved non-production data; validate counts, missing-field classifications and journal invariants. Do not mutate the connected project to manufacture a dataset.
6. Enable only deterministic emulator/test fixtures. Live business activation requires separate legal, accounting, merchant and release authorization.

## Dry-run and recovery requirements

- Use a stable run ID and resumable checkpoints, bounded batches, before/after counts, invariant totals and a redacted failure report.
- Preserve every order, entitlement, booking reference, attribution snapshot, journal fact, scan record and ownership history.
- Unknown legacy ownership or cover state remains `unknown`/review-required; never infer an entitlement-linked cover balance from a generic wallet.
- Do not rerun a partially completed operation without its checkpoint and idempotency keys.
- Compare per-event inventory and per-order entitlement counts before/after. Any mismatch blocks activation.
- Compare cover/journal totals in integer paise; any unbalanced or ambiguous record blocks financial enablement.
- Rollback disables new access grants, transfers, cover issuance and redemption server-side while preserving already-sold admission rights, existing refund paths and the ability to inspect/reconcile records.
- Pending invitations, holds, authorizations and provider refunds must be resolved or remain visibly frozen/recoverable; a flag flip must not erase them.
- No rollback deletes additive fields, history, ledger entries or outbox records.

## Local export inventory tool

`node scripts/m5-migration-dry-run.mjs --input EXPORT.jsonl --run-id RUN_ID --checkpoint CHECKPOINT.json --report REPORT.json` performs a file-only, read-only inventory over JSONL rows shaped as `{ "source": "v2_entitlements", "id": "...", "data": { ... } }`. It classifies legacy holder/credential/unit-kind fields, counts private event poster URLs and retained private poster keys against their row organization, flags rows where both values identify different managed objects, validates cover-account balance totals, and checks balanced integer-paise journal lines. Poster counts are candidate inventories only: they do not verify the configured bucket, object existence, or ACL state. It writes only a local resumable version-3 checkpoint and count-only report; it does not connect to Firebase, print row IDs/PII, repair records, or infer missing business facts. `--resume` requires the same run ID and SHA-256 input fingerprint. Unit coverage: `node --test scripts/m5-migration-dry-run.test.mjs`. This tool has only been exercised on synthetic local fixtures; it has not been run against a project export, and its inventory is not a migration/backfill or authorization to perform one.

## Implemented additive fields and query

`v2_entitlements` now reads legacy records with purchaser-as-holder, credential version `1`, and inferred `unitKind` (`RSVP-` order ids become `free_rsvp`; other legacy ticket orders become `paid`). New issuance persists `currentHolderUserId`, `credentialVersion`, and `unitKind`. Explicit `currentHolderUserId: null` remains distinct from a missing legacy field and represents purchaser custody.

The purchaser quota query uses `userId ==` and `eventId ==` on `v2_entitlements`, then filters void and non-paid ticket units in application code. A matching composite index has been added to `firestore.indexes.json`; it has **not** been deployed or emulator-validated. The hold count uses active reservations ordered by their per-event sequence and does not introduce a counter/backfill.

Ticket QR version 1 retains its prior key and payload. Credential versions above 1 derive distinct per-ticket keys and use `id:version:window:signature`; online scanner admission checks the version inside the entitlement transaction. Ticket transfer now requires `m5OfflineTicketManifests=false` and `m5OfflineManifestDrainComplete=true`; the latter is an operator attestation that the 12-hour manifest and 24-hour sync grace has elapsed after offline issuance was disabled. Gateway configuration is wired, defaults transfers off/manifests on/drain false, and is documented in `.env.example`. Transfer remains disabled until offline-manifest drain is evidenced.

Pending/complete transfer records use the additive `v2_ticket_transfers` collection. `v2_entitlements.pendingTransferId` and its version are updated in the same Firestore transaction as transfer creation/resolution; acceptance updates the current holder and credential version in that transaction. New invitations persist `recipientUserId: null` and only a SHA-256 verifier of normalized recipient email; accept/decline require a persisted verified account and the Firestore transaction rechecks the email verifier before state change. Legacy direct-account records remain readable. The transfer collection query is single-field by entitlement ID. Firestore Emulator coverage verifies concurrent creation, wrong-email rejection, matching-email claim, ownership rotation, stale-version denial, freeze, redacted outbox evidence and audited freeze-lock release. Admin freeze/release actions audit reasons; release preserves frozen transfer history and holder/credential version while clearing only the matching unused entitlement lock. No index deployment has run. Ticket routes omit recipient IDs/verifiers. Guest supports manual invite-link sharing, sign-in-gated acceptance, and sender status/link/cancel controls after reopening ticket details; no email is sent. Durable provider delivery/resend and connected acceptance remain incomplete. Transfer remains disabled pending offline-manifest disable/drain attestation.

RSVP creation now reads the Better Auth account from `v2_auth_users` through `UserAccountRepository` and requires `emailVerified === true`; missing or unverified accounts receive 403 before order or entitlement creation. The deterministic event/account order ID enforces one active RSVP order across tiers. This signal is account verification only and does not prove a unique human identity. No PII was added to RSVP orders.

RSVP group admission is rejected by `createTicketTier` and again by `CheckoutService.createRsvp` to fail closed if a malformed/legacy tier row exists. Ticket transfer request and acceptance reject free RSVP entitlements, including legacy records inferred from the `RSVP-` order ID prefix, so transfer cannot grant a recipient another free RSVP allowance. Firestore Emulator coverage verifies Better Auth's `emailVerified` decoding (`firestore-user-account.integration.test.ts`, 1 test); service coverage includes missing/unverified accounts and RSVP transfer prohibition.

Event `visibilityMode` is additive; legacy documents decode as `public`. `unlisted` events are written with `isPublic=false`, which excludes them from indexed public discovery/search without an index change. Private `code`/`invited` event detail and tiers require user-bound grants; private detail is no-store/noindex and omits long-lived public poster URLs. When a managed poster is revoked during a private transition, its validated key is retained privately and PublicService issues a five-minute signed read URL only after the grant check. Private access is feature-gated off by default. This does not establish ACL state for historical private records or revoke old external/legacy URLs; a real bucket export and ACL inventory remains required before activation. Other export/cache surfaces remain under review. Optional `addressDisclosure` (`public`, `after_grant`, `hidden`) is additive. New private events default to hidden, legacy private events without the field decode fail-closed in public detail, and exact venue address is revealed after a valid event grant only when configured. This setting does not retract data from the independent public venue profile endpoint.

Unrelated updates preserve a legacy event's stored `isPublic` value; only an explicit `visibilityMode` change recomputes discoverability. This prevents a title/summary edit from exposing a previously hidden published record. Domain regression tests cover hidden legacy rows and explicit public/unlisted changes.

New group tiers can opt into `admissionMode: per_person` with a canonical `guestCount >= 2`. The hold snapshots those values; inventory, paid purchaser limits and tier per-user caps count attendee units. Fulfillment emits deterministic per-person entitlements; one per bundle is assigned to the purchaser and remaining units stay explicitly unassigned in purchaser custody. Legacy bundle/couple entitlements retain their existing one-credential multi-admit shape. Firestore emulator validation confirmed two paid bundles of three count as six tier units and one active hold counts as three. Guest wallet mapping now displays each entitlement separately. No connected migration/backfill was run.

M5 cover uses deterministic account/entry persistence in `v2_event_cover_accounts` and `v2_event_cover_entries`. New accounts freeze `refundPolicy` from the exact accepted Venue proposal. Legacy account decoding defaults a missing policy to `saved_policy_review`; it never grants automatic refund eligibility. Memory and Firestore adapters support issuance, reserve, capture, void, and one full refund for an unused account whose frozen policy is `unused_full_before_redemption`; the refund entry references issuance and the account update is atomic. `RefundService` now permits only an initial full-order refund when every linked cover account is fully unused under that saved policy. It transactionally freezes those accounts before provider execution, keeps them frozen while the provider outcome is uncertain, releases them on definitive failure, and uses the refund request ID for idempotent cover ledger completion after canonical journal posting. Focused service/API tests and the Firestore Emulator prove pre-provider freeze ordering and that the freeze cannot race alongside a Venue reservation. Cover activation and sales/redemption remain disabled. No migration or index deployment has run. Rollback remains reader-compatible because new Event/Entitlement fields are optional; missing cover refund policy fails closed to manual review. Disabling new transfer/private-access/cover writes does not require deleting fields. Do not roll back to a scanner build that cannot parse versioned QR payloads after any ownership change has occurred. The offline-manifest drain flag is operational input and must not be asserted until evidence shows all previously issued manifests and sync-grace periods have elapsed.

Captured-redemption accounting adds `event_cover_venue_payable_held` as a journal account code. The code is deliberately absent from payout line types and payout-account selection, so these balances remain held and cannot enter payout totals. Durable `event-cover.redeemed` and `event-cover.reversed` outbox events drive balanced, idempotent journals; reversals require an exact captured ledger entry and preserve its provenance. Firestore writes the account reversal, normalized reason in the immutable reversal entry, and reversal outbox event in one transaction. Replays must match both actor and reason. A privileged Admin operation also records a reasoned before/after audit and remains behind the server-side M5 accounting approval flag. The Firestore concurrent-reversal integration test is present, but its local execution is unverified while `FIRESTORE_EMULATOR_HOST` and Firebase CLI are unavailable. Rollback must preserve the held journal account, reversal entries, outbox records, and audit history; do not reinterpret held balances as payable or remove them during rollback. No settlement-release path is implemented.

Material event-change responses add optional `eventChange` context and `eventChangeResponse` state to private `v2_social_notifications` rows; legacy notices without these fields remain valid. The response is bound to the delivered event version and ticket entitlement. The current holder may confirm updated details, while only the original purchaser may request refund review. Firestore records one response transactionally and exact retries replay; competing responses conflict. A refund-review request is not an Admin RefundRequest, does not freeze or void admission, and does not initiate provider work. Rollback may disable new response writes while preserving already-recorded response state and reading old notification rows without these optional fields.
