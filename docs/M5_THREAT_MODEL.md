# M5 Threat Model and Verification Ledger

This is an implementation-security ledger, not a launch clearance. It records source controls and tests that exist in the current dirty M4→M5 worktrees, then names the remaining gaps. It does not assert connected-project or production behavior.

## Assets and trust boundaries

- Admission entitlement, purchaser identity, current holder, QR credential version, scan history and refund/transfer locks.
- Private-event grants, tier access codes, verified-recipient transfer bindings and access to private event details.
- Cover balances, POS authorization/receipt data, merchant and Venue scope, payment/refund facts, and financial journal entries.
- Admin authority, audit records, organization membership and event/Venue partnerships.
- Boundaries: Guest browser/BFF → authenticated API → Core services → memory or Firestore repositories; Partner/Admin browser → authenticated API → tenant/platform authorization; scanner/terminal → online admission/redemption services; provider callbacks → verified payment processing.

## Threats with implemented controls

| Threat | Current controls and evidence | Remaining gap |
|---|---|---|
| Ticket ID enumeration or cross-owner ticket reads | `TicketService.getById` returns not-found unless the actor is the current holder; holder lookup uses purchaser fallback only for legacy records. Tests: `packages/core/src/application/tickets/ticket-service.test.ts`. | Run the full role-separated browser scenario; validate every wallet/CSV/support path for the same owner scope. |
| Transfer invitation theft, account-ID forgery, or recipient mismatch | New invitations persist only a normalized-email SHA-256 verifier; recipient must have a persisted verified account; Firestore rechecks the verifier transactionally. API rejects account-ID payloads. Emulator/test evidence: `packages/core/src/infrastructure/firestore/firestore-ticket-transfer.integration.test.ts`, `apps/api-gateway/src/routes/v2/tickets/ticket-routes.test.ts`. | Link secrecy/referrer/log review, delivery/resend semantics and authenticated browser sessions remain unverified. |
| Duplicate transfer or stale QR replay | Transfer creation and resolution are transactional; acceptance rotates credential version; scanner checks the current version. Emulator and scanner evidence: `packages/core/src/infrastructure/firestore/firestore-ticket-transfer.integration.test.ts`, `packages/core/src/infrastructure/firestore/firestore-refund-checkin.integration.test.ts`, `packages/core/src/application/door/scanner-service.test.ts`, `apps/api-gateway/src/routes/v2/door/scanner-routes.test.ts`. Both transfer acceptance and refund freeze are serialized against scanner admission by Firestore Emulator race tests. | Transfer/refund, cancel/check-in, cover transfer and offline manifest revocation remain open. Transfers stay disabled until drain evidence. |
| Private code brute force, replay or over-redemption | Random secret returned once, verifier-only storage, identity-bound grants, atomic max-claim enforcement, generic invalid response and `SENSITIVE_COMMAND` rate limit. Evidence: `packages/core/src/infrastructure/firestore/firestore-ticket-access.integration.test.ts`, `packages/core/src/infrastructure/memory/memory-ticket-access-repository.test.ts`, `apps/api-gateway/src/routes/v2/partner/event-catalog.test.ts`. | Add rate-limit boundary tests across distributed gateway instances; verify link/referrer/cache behavior and every alternate export/media surface. |
| Checkout overbooking or bypass of paid-unit cap | Holds are rechecked transactionally and paid entitlements plus holds count toward per-event purchaser quota. Emulator tests: `packages/core/src/infrastructure/firestore/firestore-paid-unit-quota.integration.test.ts`, `packages/core/src/infrastructure/firestore/firestore-late-capture.integration.test.ts`. | Eligibility attestations, confirmed-refund Firestore recovery and broader mixed-tier stress remain open. |
| Concurrent cover overspend or duplicate capture | `EventCoverAccountRepository` transactionally reserves/captures and replays by operation ID. Guest-confirmed terminal challenges are one-time consumed; refund freezing is serialized against both reservation and confirmed redemption consumption. Emulator evidence: `packages/core/src/infrastructure/firestore/firestore-event-cover-account.integration.test.ts`. | Cover redemption posting to the Venue payable journal, refund/reversal journal integration, challenge expiry cleanup and wrong-Venue/event authorization tests remain open. Cover sales/redemption remain gated pending approvals and runtime acceptance. |
| Admin transfer lookup leaks recipient details or is cached | Ticket-scoped Admin read requires an Admin session, limits response to 50, returns binding type but no user IDs/email verifier, and sets `private, no-store`. Route test: `apps/api-gateway/src/routes/v2/admin/tickets.test.ts`; UI test: frontend `apps/admin-console/src/app/tickets/page.test.tsx`. | Extend equivalent privacy review to all Admin exports and transfer investigation tools; test real Admin role boundaries in isolated browser contexts. |
| Cover reconciliation exposes Guest scope or implies withdrawable Venue funds | Admin-only ticket-scoped response is `private, no-store` and omits Guest/organization identifiers. The screen labels account entry consistency and explicitly excludes Venue payout availability and balance repair. Route and UI tests: `apps/api-gateway/src/routes/v2/admin/tickets.test.ts`; frontend `apps/admin-console/src/app/tickets/page.test.tsx`. | No journal-level reconciliation or held/available settlement facts exist; verify the connected Admin role and complete privacy review of other exports when runtime access is available. |
| Ticket email reaches a purchaser instead of the holder or follows stale ownership | Delivery resolves the current entitlement holder, checks persisted verified email, skips issuance duplicates for the purchaser, and rejects transfer events whose credential version is no longer current. Delivery rows use deterministic idempotency keys. Tests: `packages/core/src/application/events/transactional-email-consumer.test.ts`. | Provider delivery and recipient rendering have only mocked local evidence; test against isolated role identities before claiming connected delivery. |
| Cached API response exposes ticket, transfer, private tier or grant state | Guest ticket/wallet APIs, Partner event/catalog reads, access-code redemption and Admin ticket listing/export return `private, no-store`; private event detail/tier and rotating QR already use no-store. Focused cache-header assertions cover ticket, wallet, Partner event/catalog, public access and Admin ticket routes. | Other authenticated exports still need a systematic cache/privacy review; previously public poster URLs are not revocable through the current source workflow, so private-event artwork remains a documented gap. |

## Required negative/race coverage still open

- Forged `x-organization-id`, cross-tenant mutations and role escalation over direct HTTP for every affected endpoint.
- CSRF, cookie-scope, redirect allowlist, session expiry/revocation and permission-cache invalidation across separate Guest/Partner/Admin profiles.
- Private metadata leakage through historical public media URLs, legacy media formats, page metadata, caches, exports, venue profiles and alternate API reads. New private transitions revoke same-organization managed poster ACLs and preserve a private key for grant-authorized short-lived reads; historical bucket ACL state and alternate surfaces still need an export/inventory and runtime review.
- Transfer/refund and cancel/check-in races; cover transfer races; provider callback/recovery and refund timeout/retry races. Transfer acceptance versus scanner admission and refund freeze versus scanner admission are covered by `firestore-ticket-transfer.integration.test.ts` and `firestore-refund-checkin.integration.test.ts`; cover refund freeze versus reservation and confirmed redemption consumption are covered by `firestore-event-cover-account.integration.test.ts`.
- Cover wrong event/Venue/terminal/operator, revoked terminal, insufficient funds, expired reservation, duplicate confirmation, ambiguous receipt recovery and offline rejection.
- Duplicate RSVP and eligibility identity assurance; comp claim quota; waitlist offer ordering/expiry; upgrade failure preserving original admission; reschedule/cancellation response consistency.
- PII/logging, XSS/template content, unsafe URLs/uploads, receipt-reference spoofing, adjustment approval separation and repeated reversal abuse.

## Gate status

Automated controls above are local source/emulator evidence only. No connected `c1rcle-v2` M5 records, Razorpay Test Mode payments, production access or live financial operation were performed in this run. Keep private access, transfer, cover sales/redemption and connected acceptance at their existing server-side gates until the remaining source, approval and runtime prerequisites are closed.
